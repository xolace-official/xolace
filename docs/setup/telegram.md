# Telegram bot setup

How a Convex deployment gets its Telegram bot (#765). Telegram is the outreach layer's
second channel (#760): check-ins arrive in a private chat with the bot, and people
answer or write back there.

## Which deployment gets which bot

| Deployment | Bot | Who sets it up |
|---|---|---|
| prod | the shared Xolace bot, made in BotFather from a Xolace-owned account | an engineer, by hand, once |
| staging | a second shared bot from the same account (e.g. `xolace_staging_bot`) | an engineer, by hand, once |
| your dev deployment | a personal bot you make yourself | you |
| PR previews, e2e, agent worktrees | **none** | nobody |

A bot can point at only one webhook. Never give two deployments the same token: the
last `configureBot` wins and the other deployment silently stops getting updates.

With no bot, Telegram is `not_configured`: hidden in the app, never chosen by the
router, and the webhook answers 401. Nothing else breaks.

## What the deployment needs

One environment variable, set per deployment and **never** as a project default (a
default would hand every preview the same bot):

| Name | Value |
|---|---|
| `TELEGRAM_BOT_TOKEN` | the token BotFather gives you, `123456789:AA…` |

`CONVEX_SITE_URL` is set by Convex. The webhook secret is generated by `configureBot`;
only its SHA-256 is stored, in the `telegram_bot` table.

Never commit a token or paste it into an issue, PR or chat. If one leaks, revoke it in
BotFather (`/revoke`), set the new one and run `configureBot` again.

## Set up a bot

1. In Telegram, open [@BotFather](https://t.me/BotFather), send `/newbot`, and pick a
   name and a username ending in `bot` (for your own: `xolace_<you>_dev_bot`). Copy the
   token.
2. Set the token on the deployment. For your dev deployment, from `packages/backend`:

   ```sh
   bunx convex env set TELEGRAM_BOT_TOKEN '<token>'
   ```

   Staging and prod: the Convex dashboard → the deployment → **Settings** →
   **Environment Variables**. An agent never sets env on staging or prod.
3. Make sure the deployment runs code that has the webhook route (`/telegram/webhook`).
   For your dev deployment that's `bun run dev:server`; staging and prod get it from
   their pipelines.
4. Run the setup action on that deployment:

   ```sh
   bunx convex run outreach/telegram/bot:configureBot
   ```

   (Staging or prod: the dashboard → **Functions** → `outreach/telegram/bot:configureBot`
   → **Run**.) It:
   - calls `setWebhook` with `<CONVEX_SITE_URL>/telegram/webhook`, `allowed_updates`
     `message`, `callback_query`, `my_chat_member`, and `drop_pending_updates: false`;
   - generates a fresh secret and stores its hash plus the bot's `getMe` username;
   - sets the bot's name, description, short description and its `/help` command
     from `convex/outreach/telegram/copy.ts`. `/stop` is set per chat when it links
     and removed when it unlinks.
5. Message the bot. As a stranger (no linked Xolace account) you get the fixed reply
   once; another message within 24 h gets nothing.

`configureBot` is idempotent: run it again whenever you like. Each run **rotates the
secret**, so updates signed with the old one are refused from then on. It never runs on
deploy.

## Turning Telegram on

A configured bot isn't enough for outreach to use it: the `outreach_channels` row for
`telegram` (absent = disabled) is the kill switch and the free/Plus gate. That's an
admin config edit, not part of this runbook.

With the row on, a signed-in user can link a chat: `outreach/telegram/link:createLink`
returns `https://t.me/<bot>?start=<token>` (one use, 15 minutes, 10 mints an hour), and
opening it sends `/start <token>` to the bot, which links the chat and answers with the
welcome line. A bad, used or expired token gets the "This link has expired" line. The
token is never stored or logged: the webhook keeps only its SHA-256.

A link ends from either side: **Unlink** in the app (goodbye line), `/stop` in the chat,
blocking the bot, or any 403 on a send. Each leaves the row `revoked` with its reason
and appends a consent `revoked` row; the app shows "disconnected". **Pause** in the app
stops outreach but the chat can still write to the bot. Linking the same chat from
another account, or a new chat from the same account, moves the link and tells the old
side. A daily cron (`purge revoked telegram links`) deletes revoked rows 30 days after
they were revoked; after that the chat is a stranger again.

## Drift check

A daily cron (`check telegram webhook`) calls `getWebhookInfo` and logs an error when:

- the webhook URL isn't this deployment's `<CONVEX_SITE_URL>/telegram/webhook`
  (someone ran `configureBot` for this bot on another deployment);
- Telegram recorded a delivery error in the last 24 h;
- the pending update count grew since the last check.

It never re-points the bot. Read the log line, fix the cause, and rerun `configureBot`
on the deployment the bot belongs to. On a deployment with no bot it does nothing.

## Troubleshooting

| Symptom | Fix |
|---|---|
| `configureBot` fails with `TELEGRAM_BOT_TOKEN is not set` | Step 2 on that deployment. |
| `configureBot` fails with `(401)` from `getMe` | The token is wrong or was revoked. Get it from BotFather again. |
| The bot never replies | Check the drift log, then rerun `configureBot`. The webhook must be on a deployment that has the route. |
| Every webhook post gets 401 | No `telegram_bot` row or no token here, or the secret was rotated by a newer `configureBot` (on this or another deployment). Rerun it here. |
